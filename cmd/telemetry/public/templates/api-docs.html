API

Everything the dashboards show comes from the JSON endpoints on this page. They answer GET requests at https://telemetry.community-scripts.org and need no account.

Access

What is public, and what the trace password adds.

  • Without a header every endpoint answers, but leaves out the text a failed run reported: error (the trace), error_message, error_step and failed_command. Runs carry traces_withheld: true, and every cause is its exit code (kind: "exit_code", key: "exit 100").
  • With Authorization: Bearer <trace password> those fields are filled, and causes are grouped by error message, or by the failing command for older reports. Maintainers hand out the password.
  • Any other Authorization header answers 403. Requests are limited per client address, 300 a minute unless the service is configured otherwise; past that the answer is 429.
  • Cause keys differ with and without the password, so do not mix answers from both.

How runs are counted

The same rules apply to every figure.

  • A run is one script execution: all reports that share an execution_id. Its status is success, failed, aborted (cancelled or declined by the user), unknown (no result: it stopped reporting) or in_progress.
  • failure_rate is failed divided by success plus failed, in percent. Aborted runs, runs without a result and running runs are not part of it.
  • setups counts distinct combinations of CPU, GPU, RAM speed, host version and kernel, so one host that retries stays one setup.
  • days=1 is today since 00:00 UTC; days=7 is today and the six days before it. Timestamps are UTC.

Filters

Every endpoint below takes these unless it says otherwise. An unknown value answers 400 and names the accepted ones.

ParameterValues
days1 to 365. The default differs per endpoint and is listed with it.
repoProxmoxVE, DevScripts, external (any other repository) or all (default).
slugOne repository as owner/repo, for example community-scripts/ProxmoxVE. /api/repo-slugs lists them.
platformpve, incus or all (default).
typelxc, vm, turnkey, pve and tool (host tools), addon, all, or install for everything except host tools and add-ons.
appThe exact script name, for example immich.

Failures

Default period 7 days, default type install.

GET /api/errors
The whole error analysis in one answer: summary (runs per status, failure_rate, apps_failing), causes (up to 50), apps (apps with a failed run), exit_code_stats, category_stats, failures_over_time (by the hour for days=1, else by the day; bucket says which), stuck (runs of the last 24 hours without a result) and min_runs (the finished runs an app needs before the dashboard ranks its rate).
GET /api/causes
Failed runs grouped by what went wrong. Each cause has key, kind (message, command or exit_code), message, category, exit_code, exit_description, failures, apps, top_apps, setups, first_seen, last_seen, last_24h, prev_24h, trend (new, rising, steady, falling, stopped, quiet) and examples (up to three run IDs). examples=full adds those runs as example_runs. limit defaults to 50 and goes up to 200.
GET /api/app-errors
Apps with at least one failed run, most failures first: runs per status, failure_rate, setups_failed, top_cause, top_cause_message, top_exit_code, last_failure, last_success and failing_now (the last failure is newer than the last success). limit defaults to 100 and goes up to 500.

Single runs

Default period 1 day, default type all.

GET /api/records
One record per run, newest first, as records with total, page and total_pages. Further filters: status (a status from above, or the stage of a running run: installing, validation, configuring), cause (a cause key), exit_code, category, os, search (part of the app name), execution_id, random_id and, with the password, message (an exact error message). page starts at 1, limit defaults to 50 and goes up to 100, sort takes created, nsapp, status, os_type, type, method, exit_code or duration, with a leading - for descending.

A record holds the app (nsapp, type, app_version, repo_source, repo_slug), the result (status, exit_code, exit_description, error_category, cause, cause_kind, error_phase, failed_function, failed_line), the timing (started_at, finished_at, duration in seconds, last_stage, stages with the seconds spent in each), the guest (os_type, os_version, core_count, ram_size in MB, disk_size in GB, ct_type, method) and the host (platform, pve_version, kernel_version, arch, cpu_vendor, cpu_model, gpu_vendor, gpu_model, gpu_passthrough, ram_speed). With the password it also holds error, error_message, error_step and failed_command.

Dashboard and scripts

The figures behind the other two pages.

GET /api/dashboard
Default period 1 day, default type install. summary, total_all_time, apps (the 15 with the most runs), breakdown (runs by platform, type and os), top_causes, failing_apps (the highest failure rates among apps with at least min_runs finished runs), failure_matrix (failed runs per app and cause) and timeline (runs, failed and aborted per bucket). Also takes cause.
GET /api/scripts
Default period 30 days, every type. top_scripts holds one entry per script: total, runs per status, failure_rate, setups_failed, failing_now, last_failure, last_failure_cause and last_success. Takes days, repo, slug and platform only.
GET /api/script-detail
Needs app. Default period 30 days, default type all. One script's runs per status, daily (by the hour for days=1), causes (up to 10), exit_codes, breakdown by platform and os, and recent (its newest 15 runs as records).
GET /api/repo-slugs
The repositories that reported runs, with their counts. Takes days (default 30) and repo.
GET /api/exit-codes
Every known exit code with its description. Takes no filters.

Examples

Replace $PASSWORD with the trace password, or leave the header out.

What failed in the last seven days, and how often:

curl -s -H "Authorization: Bearer $PASSWORD" "https://telemetry.community-scripts.org/api/causes?days=7&limit=20"

Every failed run of one cause. Take key from the answer above and URL-encode it:

curl -s -G -H "Authorization: Bearer $PASSWORD" "https://telemetry.community-scripts.org/api/records" \
  --data-urlencode "days=7" --data-urlencode "status=failed" --data-urlencode "limit=100" \
  --data-urlencode "cause=E: Unable to locate package libvips-dev"

One script over the last 30 days:

curl -s -H "Authorization: Bearer $PASSWORD" "https://telemetry.community-scripts.org/api/script-detail?app=immich&days=30"

Analysis with an AI assistant

Any assistant that can send a GET request with a header can read this API.

Give it the address of this page and, if it should read failure text, the trace password to send as Authorization: Bearer. A sequence that works well:

  1. /api/errors?days=7 for the overview: how much fails, which causes and which apps.
  2. /api/causes?days=7&examples=full for each cause with up to three complete example runs, traces included.
  3. /api/records?status=failed&cause=… or &app=… when it needs every run of one cause or app. A page holds at most 100 runs; total_pages says how many there are.
  4. /api/script-detail?app=… for one script over time.
  • The password also allows POST /api/github/create-issue, which opens a public GitHub issue. Tell an assistant to send GET requests only, unless it is meant to open issues.
  • With the password, the assistant and its provider receive the failure text. Credentials and e-mail addresses are masked when a report arrives, but the text is behind a password because it is the least filtered data here.
  • Answers are cached: up to two minutes for periods of at most 7 days, up to a day for longer ones. /api/records is not cached.
